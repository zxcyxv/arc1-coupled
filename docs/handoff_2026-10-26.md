## 1. 지금 상태 (10-25 끝)

**레포.** 이 레포(`arc1-coupled`)는 아직 커밋하지 않았다. GitHub 레포를 만들고 푸시하는 것은 사용자가 한다. `runs/`는 gitignore 대상이다.

**확인한 것**

| 항목 | 결과 |
|---|---|
| 모델 = 기존 `lt/coupled.py` | 같은 seed에서 초기 가중치 동일. 출력은 Γ 없으면 비트 단위 동일, Γ 있으면 차이 2.8e-14(FP64) |
| 데이터 = TRM | 바이트 단위로 같음. ARC-1은 학습 캔버스 3,633,410개 + 시험 385,815개, ARC-2는 학습 5,163,277개 + 시험 170,393개(§8) |
| 옵티마이저 = TRM | `adam-atan2 0.0.3` 커널 식과 원소별로 같음(테스트) |
| DDP | CPU에서 2프로세스(gloo) = 1프로세스 grad_accum 2(가중치 차 ≤ 1e-12). 재개 후 가중치가 끊김 없이 돈 런과 비트 단위로 같음 |
| 운영 흐름 | 5090에서 bench → start → status → stop(SIGTERM) → 재개 → quick/vote/final 평가 → 제출 파일까지 통과 |
| 단위 테스트 | 26개 통과(`python -m unittest tests.test_model tests.test_data tests.test_evaluate tests.test_train`) |
| 따로 돌리는 평가(`run.sh eval`) | 컴파일 경로로 정상 동작. 5090에서 원본 판 평가 104초(컴파일 포함) |

**실측 (5090, 전력 400 W 제한 상태, 역전파 2블록, Γ 포함)**
- 레인당 4.79 ms/step.
- 메모리: GPU당 192레인이면 grad_accum 1로 약 66 GiB, 2로 약 39 GiB(추정 분해: 활성 0.29 GiB/레인, carry 0.055 GiB/레인).
- Γ의 틀 attention을 BF16 flash로 하면 FP32보다 10.6% 빠르고, κ 차이는 최대 1.3e-2다.

**예측 (4×H100 SXM)**
- 5090 실측을 대역폭 비율(3.35 / 1.79 TB/s)로 환산하면 약 0.49 s/step이다(±30%).
- ARC-1 50k 에폭(259,113스텝)은 약 1.5일, ARC-2 50k 에폭(약 36만 스텝)은 약 2.1일.
- 1001판 최종 평가는 ARC-1 약 3시간, ARC-2 약 1시간.

## 2. 내일 순서

```bash
# 0. 인스턴스: 4×H100 SXM, on-demand, 디스크 50~60 GB. Max CUDA 12.4여도 된다(setup이 cu126을 깐다).
git clone <레포 URL> && cd <레포>          # 토큰은 사용자가 준비

# 1. 환경 확인 (약 10분, torch 설치 포함)
bash scripts/run.sh setup
#   기대: torch 2.11.0+cu126(또는 cu128), "matmul + torch.compile ok on every GPU", NCCL ok
#         (실패하면 P2P를 끄고 다시 시도해 runs/env.sh에 기록), 데이터 sha OK 2개, 테스트 OK

# 2. DDP가 단독보다 느리지 않은지 + 설정 고르기 (약 15분)
NGPU=1 BENCH_GA=2 EXTRA="global_batch_size=192" bash scripts/run.sh bench   # GPU 1장, 192레인: 기준
bash scripts/run.sh bench                                                   # GPU 4장, 768레인: 마지막에(runs/bench.json을 씀)
#   판정: 4장의 s/step이 1장 192레인의 s/step과 같거나 +5% 이내여야 한다(같은 GPU당 일, 통신만 추가)

# 3. 시험 런: 4 GPU에서 처음부터 끝까지 (약 10분)
export TRIAL="max_steps=192 quick_eval_epochs=10 vote_eval_epochs=20 vote_versions=2 save_every_steps=64 final_versions=2"
RUN=trial EXTRA="$TRIAL" bash scripts/run.sh start
RUN=trial bash scripts/run.sh status        # 몇 번 확인
RUN=trial bash scripts/run.sh stop          # 100스텝 무렵: "stop requested: checkpoint step N"과 EXITCODE 0
RUN=trial EXTRA="$TRIAL" bash scripts/run.sh start    # "RESUME runs/trial/step_N.pt"
#   끝나면 확인: runs/trial/eval.jsonl에 quick(64), vote(112), quick(160), final(192). submission_step_192.json(400과제).
rm -r runs/trial

# 4. ARC-1 본 런
bash scripts/run.sh start                   # RUN=arc1, configs/arc1.json, 50k 에폭
bash scripts/run.sh status

# 5. ARC-1 마무리
#    끝까지 돌면 최종 평가가 자동으로 붙는다(1001판, 약 3시간).
#    포화해서 멈출 때: stop -> 마지막 체크포인트로 평가
bash scripts/run.sh stop
CKPT=runs/arc1/step_N.pt bash scripts/run.sh eval       # runs/arc1/eval_N_all.json, .submission.json
bash scripts/run.sh archive                 # 로그 -> docs/evidence/run_arc1, milestone -> checkpoints/run_arc1
git add docs/evidence/run_arc1 && git add -f checkpoints/run_arc1/*.pt && git commit -m "Archive arc1" && git push
# 학습 뒤 중간 시점의 1001판 평가: CKPT=checkpoints/run_arc1/step_N.pt bash scripts/run.sh eval (ARC-1 약 3시간)

# 6. ARC-2 (ARC-1 최종 평가가 끝난 뒤. 같은 GPU를 쓴다)
RUN=arc2 CONFIG=configs/arc2.json bash scripts/run.sh start
RUN=arc2 bash scripts/run.sh status
```

## 3. 지켜볼 것과 대응 (체크리스트)

**시작 후 30분**
- [ ] `status`의 s/step이 bench 값과 ±10% 이내인가. ETA가 예상(ARC-1 약 1.5일)과 맞는가.
- [ ] GPU 이용률이 약 99%인가. 메모리 피크가 75 GB 이하인가.
- [ ] `clocks_event_reasons`:
  - `0x4`(소프트웨어 전력 상한)는 흔하다.
  - `0x8`(HW slowdown), `0x20`/`0x40`(열)이 계속 뜨면 느려진다. 속도와 같이 보고, 심하면 다른 매물로 옮기는 것을 검토한다(체크포인트를 들고 가면 재개된다).
- [ ] 손실이 줄어드는가. lr은 2,000스텝까지 워밍업한다.
- [ ] 2,048스텝에 `runs/arc1/step_2048.pt`(약 60 MB)가 생기는가.

**하루 동안**
- [ ] quick 평가(원본 판 1개)는 1천 에폭(약 5,184스텝)마다, vote 평가(8판)는 5천 에폭(약 25,920스텝, 약 3.5시간)마다 `eval.jsonl`에 쌓인다. 1001판은 마지막에 한 번만 한다(decisions.md의 "평가 세 종류").
- [ ] vote 평가 때마다 milestone(EMA, 15 MB)이 `runs/<런>/milestones/`에 생긴다. `archive`가 `checkpoints/run_<런>/`으로 복사하니, `git add -f`로 올려 두면 학습 뒤 아무 시점이나 1001판 평가를 할 수 있다.
- [ ] 멈출 시점을 판단한다(사용자). 근거로 삼은 곡선과 규칙을 적어 둔다. 시험 세트 곡선으로 고르는 것이라 논문에 써야 한다.
- [ ] vote 평가 때마다 `archive` → 커밋 → 푸시를 한다. `/workspace`가 볼륨이 아닐 수 있다.
- [ ] `df -h`를 본다. 런 하나가 약 1 GB, compile 캐시가 약 1~2 GB다.

**문제가 생기면**

| 증상 | 대응 |
|---|---|
| `FloatingPointError`(손실이나 기울기 비유한)로 정지 | 마지막 체크포인트는 남아 있다. 같은 명령으로 다시 시작하면 재개된다. 같은 곳에서 반복되면 lr을 낮추거나 clip을 켜야 하는데, 둘 다 TRM 레시피에서 벗어나므로 사용자와 정하고 기록한다 |
| 시작 직후 OOM | `GA=4 bash scripts/run.sh start` |
| 진행이 멈춤(로그가 안 늘고 GPU가 0% 또는 100%로 고정) | NCCL 정지일 가능성. `stop`이 안 되면 워커 PID를 kill한다(`pkill -f` 금지). `echo 'export NCCL_P2P_DISABLE=1' > runs/env.sh`로 두고 다시 시작 |
| bench보다 느림 | throttle 이유, 다른 프로세스, `nvidia-smi topo -m`(NVLink 여부) 확인 |
| cu126에서 `torch.compile` 오류 | `EXTRA="compile=false"`로 시작하면 컴파일 없이 돈다(느림). 시험 런에서 미리 드러난다 |
| EXITCODE가 0이 아님 | `runs/<런>/stdout.log` 끝을 보고 원인을 잡은 뒤 같은 명령으로 재개 |

## 4. DDP가 단독보다 느려지지 않는 이유

- GPU마다 자기 192레인을 따로 계산한다. 스텝마다 통신은 기울기 하나를 평탄화한 all-reduce(370만 개 FP32, 약 15 MB)와 아주 작은 all-reduce 두 개(유한성 플래그, 지표 5개)뿐이다. 레인 교체 때는 정지 플래그 하나가 더 있다.
- NVLink(매물 표기 478 GB/s)에서 15 MB는 0.1 ms 수준이다. P2P 없이 PCIe로 가도 수 ms라, 0.5 s 스텝의 1% 미만이다.
- DDP 래퍼 훅도, 버킷별 동기화도, 데이터로더 워커도 없다. 레인은 16스텝마다 한 번 CPU에서 만든다(약 10~20 ms).
- torchrun은 프로세스마다 `OMP_NUM_THREADS=1`로 둔다.
- 정확성(기울기와 가중치가 같음)은 테스트로 확인했다. 속도 확장은 GPU가 한 장뿐이라 확인하지 못했다. 그래서 §2의 2번(1장 192레인과 4장 768레인의 s/step 비교)으로 확인한다.
